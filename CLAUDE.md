# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Predicta is a thesis project: a sales analytics and forecasting platform for retail SMEs. `backend/` is a FastAPI + SQLAlchemy 2.0 + PostgreSQL API; `frontend/` is a React 19 + TypeScript + Vite SPA that consumes it. `AGENTS.md` holds the same rules for other agents; keep both files consistent when changing a rule. Python 3.14 in CI (code needs 3.12+), Node 24.

## Commands

Backend (from `backend/`, with `venv` active):

```bash
pip install -r requirements.txt -r requirements-dev.txt
uvicorn app.main:app --reload                             # port 8000
alembic upgrade head
alembic revision --autogenerate -m "description"
python scripts/generate_dataset.py                        # -> backend/ventas_*.csv (gitignored)
ruff check app/                                           # lint, includes security rules (S, flake8-bandit)
ruff check --fix app/ && ruff format app/                 # only when intentionally reformatting
mypy                                                      # typecheck (pyproject sets files = app)
python scripts/evaluate_models.py                         # regenerate docs/evaluacion/
python scripts/run_experiment.py                          # thesis experiment -> docs/resultados/metricas_<date>.json
python scripts/measure_concurrency.py                     # needs local PostgreSQL; -> docs/evaluacion/concurrencia.md
pytest --cov=app --cov-report=term-missing                # full suite
pytest tests/test_auth.py                                 # single file
pytest -k test_register                                   # single test by name
```

Frontend (from `frontend/`):

```bash
npm install
npm run dev                          # Vite on http://localhost:5173
npm run lint                         # eslint .
npm run typecheck                    # tsc -b
npm test -- --run                    # Vitest, single run (plain `npm test` watches)
npx vitest run src/api/auth.test.ts  # single test file
npm run build                        # tsc -b && vite build
npm run e2e                          # Playwright: real API on PostgreSQL (predicta_e2e) + production build
```

Before submitting: backend `ruff check app/`, `mypy`, `pytest --cov=app`; frontend `npm run lint`, `npm run typecheck`, `npm test -- --run`, `npm run build`. CI (`.github/workflows/ci.yml`, every push) also runs `alembic upgrade head`, `alembic check`, `alembic downgrade -1`, `alembic upgrade head` against PostgreSQL 17, so a model change without a matching migration fails CI. CI also fails on a high or critical vulnerability in production dependencies (`pip-audit -r requirements.txt`, `npm audit --omit=dev --audit-level=high`) and on any secret in the git history (`secrets` job, gitleaks); every ignored advisory carries its reason in `ci.yml`.

## Environment

- `app/core/config.py` (`pydantic-settings`) is the only place that reads the environment and `backend/.env`; declare every new variable there and in `.env.example`. `DATABASE_URL` (`postgresql+psycopg2://...`) and `SECRET_KEY` are required, so importing the app without them fails. Optional: `ENVIRONMENT` (`development`/`test`/`production`, unset means production), `CORS_ORIGINS` (comma-separated, default `http://localhost:5173`; `*` only with `ENVIRONMENT=development`), `ACCESS_TOKEN_EXPIRE_MINUTES`, `LOG_LEVEL`, `MAX_UPLOAD_ROWS`, `TRUSTED_PROXIES` (comma-separated IPs or networks whose `X-Forwarded-For` gives the client IP, default `127.0.0.1`; `*` only when the app is reachable solely through the provider's proxy). With `ENVIRONMENT=production` startup fails unless `SECRET_KEY` has 32+ characters (not the `.env.example` placeholder) and `DATABASE_URL` carries `sslmode=require`, `verify-ca` or `verify-full`; a local `backend/.env` therefore needs `ENVIRONMENT=development`. Mail: `EMAIL_BACKEND` (`console`, the default, logs each message; `smtp` sends with STARTTLS through `SMTP_HOST`, `SMTP_PORT` (587), `SMTP_USER`, `SMTP_PASSWORD`; `brevo_api` posts to Brevo's HTTPS API with `BREVO_API_KEY`, used on Railway because Hobby blocks outbound SMTP), `EMAIL_FROM`, and `FRONTEND_URL` (base of e-mailed links); production requires `smtp` or `brevo_api` with its variables and an `https://` `FRONTEND_URL`. Logging goes through `app.main.add_log_sink`, which turns off loguru's `diagnose` and `backtrace` so tracebacks never print local values such as passwords (`tests/test_logging.py`).
- Passwords are hashed with `bcrypt` directly (no `passlib`) and limited to 72 bytes; new users get the `Usuario` role looked up by name.
- App startup (`lifespan` in `app/main.py`) runs `SELECT 1` and aborts if the database is unreachable.
- `tests/conftest.py` sets `DATABASE_URL=sqlite:///:memory:` *before* importing the app, overrides `get_db` with a fresh in-memory SQLite DB per test (built via `Base.metadata.create_all`, test-only), and disables the slowapi rate limiter (`tests/test_rate_limit.py` re-enables it per test). With `TEST_DATABASE_URL` set to a disposable PostgreSQL database, the same suite runs on PostgreSQL instead (tables are truncated before each test); CI runs both. Use the `client`, `user_credentials`, and `auth_headers` fixtures for authenticated requests, and `second_user` for another user's headers; they create users whose e-mail is already confirmed. The autouse `outbox` fixture captures every e-mail instead of sending it (`last_token(address)`, `confirm_email(client, address)` and `register_verified(client, credentials)` in `conftest.py` open the link like the owner would). Every private endpoint must be listed in `tests/test_isolation.py::PRIVATE_CASES`.
- Frontend reads `VITE_API_URL` (default `http://localhost:8000`). Production builds inject a CSP `<meta>` whose `connect-src` is that origin (`frontend/csp.ts`, plugin in `vite.config.ts`, builds only because the dev server needs inline scripts); `frontend/vercel.json` repeats the policy plus `frame-ancestors` as a header, and `src/test/csp.test.ts` keeps both equal. On Vercel the build fails if `VITE_API_URL` and the `connect-src` of `vercel.json` disagree. Deployment (Vercel + Railway via `backend/railway.json` + Neon + Brevo) is documented step by step in `docs/despliegue.md`.

## Backend architecture

- `app/main.py::create_app(settings)` builds the app (module-level `app = create_app(settings)`); it wires, outermost first, uvicorn's `ProxyHeadersMiddleware` (`TRUSTED_PROXIES`), `SecurityHeadersMiddleware` (`nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, CSP `default-src 'none'`, HSTS only in production, `Cache-Control: no-store` under `/users`, `/etl`, `/analytics`), CORS, `BodySizeLimitMiddleware` (413 past 26 MB on `/etl/*` and 1 MB elsewhere, by `Content-Length` or counted bytes), and the generic-500 middleware; then loguru logging, health probes (`/health`, `/health/db`), and three routers: `user_routes` (`/users`), `etl_routes` (`/etl`), `analytics_routes` (`/analytics`). Production hides `/docs`, `/redoc` and `/openapi.json`; `GET /` returns name and version.
- **Rate limits** (slowapi, per client IP, in-memory so one worker): the limits are constants in `app/core/rate_limit.py` — login 5/min, register 3/min, `/etl` uploads 10/min, forecasts and reports 20/min (`COMPUTE_LIMIT`), and `GLOBAL_LIMIT` 120/min for every other route through the app-wide dependency `enforce_default_limit` (slowapi's middleware cannot see routes inside FastAPI's included routers). Counters are keyed by endpoint, so path parameters do not split them. A new costly route declares `@limiter.limit(...)` with a `request: Request` parameter. 429 answers `{"detail": "Demasiadas solicitudes. ..."}` with `Retry-After`. Requests rejected by validation (422) never reach the decorator and are not counted.
- **Auth:** OAuth2 password flow at `POST /users/login` (form field `username` is the email) returns a PyJWT token whose `sub` is the user id. The right password on an unconfirmed account answers 403: registration sends a 24-hour single-use link to `{FRONTEND_URL}/verificar-correo#token=...` (token in the fragment), which the SPA posts to `POST /users/verificacion/confirmar`; `POST /users/verificacion/reenviar` always answers the same message. `PUT /users/me` needs `password_actual` to change the e-mail; the new address waits in `correo_pendiente` (login keeps the current one) until its link is opened, and the old address gets a notice. Every e-mail goes through `services/email_service` (queued with `BackgroundTasks`, failures only logged); Every single-use token goes through `services/token_service`, which stores only its SHA-256 in `tokens_usuario`. Every JWT carries `ver` (the user's `version_token`); `get_current_user` answers 401 when it is missing or old, and the only way to close sessions is raising `version_token` (password change or reset). `PUT /users/me/password` needs the current password and returns a fresh token; `POST /users/contrasena/olvido` (same answer always) mails a 30-minute link to `{FRONTEND_URL}/restablecer-contrasena#token=...`, posted to `POST /users/contrasena/restablecer`, which also lifts a lockout and marks the e-mail verified. Login order: unknown e-mail 401 (bcrypt still runs against `security.DUMMY_HASH`), locked 423, wrong password 401 (the 10th in a row locks the account 15 minutes, answers 423 and mails a reset link), unverified 403. Timing constants and the single clock `security.utcnow` (tests swap it with the `clock` fixture) live in `app/core/security.py`. `app/api/deps.py::get_current_user` resolves it; `require_role("Administrador")` gates by role. Do not reintroduce `python-jose`.
- **Multi-tenancy:** every `Venta`/`Prediccion` query must be filtered by the current user's `id_usuario`; tests assert per-user isolation.
- **ETL** (`etl_routes.py` maps errors to HTTP; parsing/validation/loading live in `services/etl_service.py`): uploads are size-limited and SHA-256 hashed — re-uploading the same file for the same user is rejected via `CargaArchivo` (`DELETE /etl/clear-history` removes sales and hashes). Parses CSV (auto-detects `,` `;` tab; UTF-8 with cp1252 fallback), XLSX, and `.sql` files (only `INSERT ... VALUES` is parsed — SQL is never executed). Rows are validated before building `Venta` (no silent `0.0` amounts or "today" dates; `cantidad` defaults to 1, negatives rejected); insertion is transactional; the response reports read/inserted/rejected counts with bounded per-row errors. Column mapping: `POST /etl/analizar-columnas` returns the headers, a 5-row sample, and a proposal per role from `services/column_mapping.py` (exact name or synonym only, no fuzzy matching; it is the single place for synonyms, including the English headers of the real datasets tested in task 036 and kept in `tests/test_column_mapping.py`). The upload page shows it for review and always sends `mapeo` (JSON `{rol: columna}`) to `/etl/upload-ventas`; without `mapeo`, CSV/XLSX must use the exact names and SQL reports missing columns per row. Without a `monto` column, `build_venta` derives it from `precio_unitario * cantidad`. Plain numbers are never dates, and an empty XLSX category becomes "General".
- **Categories:** `services/category_service.normalize_category` is the single canonicalization point (case/whitespace/accents) used both on ingest and on report filters; unknown categories are preserved, not mapped to "General". `normalize_product` (single spaces, each word capitalized, accents kept) is the product counterpart, applied on ingest and by migration `0006`; product filters match it by equality and always need a category (`producto` without `categoria` → 422).
- **ML** (`app/ml_models/forecast.py`, documented in `docs/ml-models.md`): `statsmodels.OLS` with an intercept and separate targets for `monto` and `cantidad` over the same features. `monthly_forecast_series` is the single monthly path: an incomplete last month is left out of the fit and projected first; fewer than 6 complete months raises `InsufficientHistoryError`; 6–23 months fit trend only (`mes_indice` = calendar months elapsed) with a horizon of half the months; 24–35 months fit trend only with a 12-month horizon; 36+ months with every calendar month observed add `mes_2`…`mes_12` (January is the reference). Seasonality starts at 36 because with 24 it lost to the same-month-last-year baseline in the backtest. Points from month 7 are flagged `extrapolacion`. The daily model grows from mean (2 days) to trend (3+) to trend + `dia_2`…`dia_7` (14+ days, Monday reference). Intervals are 95 % observation intervals from `get_prediction`, clipped at zero. Monthly metrics (R², MAPE, MAE, RMSE, WAPE, MASE, improvement over the best baseline; MAE and RMSE via `sklearn.metrics`) come from refitting at each of the last 6 months and predicting the next one unseen (`app/ml_models/evaluation.py`); unavailable metrics stay `null`. Daily metrics use a chronological last-20% holdout. `scripts/evaluate_models.py` regenerates `docs/evaluacion/`; rerun it whenever model features change. `scripts/run_experiment.py` is the single-command thesis experiment (generate with seed 2026, load through the ETL on in-memory SQLite, fit, write `docs/resultados/metricas_<date>.json` with the commit and the hypothesis result). `GET /analytics/forecast` also returns `coeficientes` (β of the final fit per predictor). Months/days without data are absent, never zero-filled. Routes call this module rather than training models inline.
- **Analytics** (`analytics_routes.py`, a thin layer over `services/analytics_service.py`, `report_service.py`, and `prediction_service.py`): stats/categories/temporal/series endpoints share the inclusive `fecha_desde`/`fecha_hasta` range (inverted range → 422). No GET writes: `/predict` (next day) and `/forecast?categoria=&producto=` (monthly series) only read, and history too short to project answers 422 with a Spanish `detail`. `POST /predicciones` recomputes on the server and saves one row per projected month under one `lote`; `GET /predicciones` pages saved batches. `GET /productos?categoria=` lists one category's products for the dependent product selects on /predictions and the sales history. Every JSON route declares `response_model`. Excel and PDF exports (Matplotlib `Figure` objects + FPDF2) live in `report_service`.
- **Field rules:** user-facing text limits and patterns live as constants in `app/schemas/schemas.py` and are repeated in `frontend/src/lib/fieldLimits.ts`; `tests/test_field_limits_contract.py` fails if they differ. Emails are stored trimmed and lowercase and looked up case-insensitively. Text params reject control characters. 422 bodies carry only `loc`, `msg` and `type` (never the submitted `input`). Every Excel export passes text through `report_service.neutralize_formula`.
- **Errors:** 500 responses and `/health/db` return generic Spanish messages; full exceptions go only to logs. Never put `str(exc)` in a response body.
- **Schema:** Alembic-only (`backend/alembic/versions/`). Never add runtime `create_all()`. After model changes, autogenerate a migration, review it manually, and check that it downgrades.

## Frontend architecture

- `src/api/http.ts` is the shared Axios instance: it injects the Bearer token from the Zustand `authStore` (persisted to localStorage) and, on any 401, clears the session and dispatches a `predicta:unauthorized` window event that `App.tsx` turns into a redirect to `/login`.
- `src/api/*.ts` hold one typed client per backend area (auth, etl, analytics, forecast, reports) with matching types in `src/types/`; server state goes through TanStack Query. Forecasts are fetched only on explicit user action (no auto-fetch or refetch-on-focus), and report downloads are handled as blobs. The upload page accepts up to 50 files per selection: it analyzes and uploads them one at a time in natural name order through the same two ETL endpoints, files with identical headers share one reviewed mapping, a failed or duplicate (409) file does not stop the rest, and `UploadBatchTable` reports each file; ordering, grouping and totals live only in `src/lib/uploadBatch.ts`.
- Routing (`App.tsx`): public `/`, `/login`, `/register`, `/verificar-correo`, `/olvide-contrasena` and `/restablecer-contrasena` (the link pages read `#token` through `lib/linkToken.ts`, which drops it from the URL); everything else sits behind `ProtectedRoute` + `AppShell`, with Dashboard/Predictions/Reports lazy-loaded.
- Forms use React Hook Form + Zod (`src/lib/authSchemas.ts`); styling is Tailwind CSS v4 with hand-written primitives in `src/components/ui/`; charts use Chart.js via react-chartjs-2, wrapped in the accessible `ChartFrame`.
- Tests (Vitest + React Testing Library, jsdom, setup in `src/test/setup.ts`) sit next to the code as `*.test.ts(x)`. End-to-end specs live in `frontend/e2e/` (Playwright, `npm run e2e`): `backend/scripts/e2e_server.py` recreates the throwaway database `predicta_e2e` (or `E2E_DATABASE_URL`), migrates and seeds it with the thesis dataset and a confirmed user, and starts uvicorn on port 8001; the specs log in once, fail on any console error, and save screenshots to `docs/evaluacion/capturas/`. Locally they use the installed Chrome; CI runs them in the `e2e` job. Chart data tables are hidden with `sr-only` on a wrapping `div`, because a table ignores `width: 1px` and would widen the page.

## Conventions and workflow

- Code, docstrings, and comments are in English; user-facing API messages and UI text are in Spanish.
- Ruff runs the security rules (`S`, flake8-bandit); every `# noqa: S...` states its reason.
- Work is planned in `docs/planning/TASKS.md` (status table) with one detailed plan per task in `docs/planning/plans/NNN-*.md`. When executing a task, read its plan fully, run each listed verification, stop and report on any STOP condition, and update the task status in `docs/planning/TASKS.md`. Do not edit the root `README.md` as part of these tasks, and do not add an index inside `docs/planning/plans/`.
- Commits follow Conventional Commits on feature branches (GitHub Flow).
- Project skills: `.agents/skills/` is the source of truth (opencode, tracked by `skills-lock.json`); `.claude/skills/` is a copy for Claude Code (without the opencode-only `agents/` subfolders). `code-review` is copied as `code-review-spec` to avoid shadowing Claude Code's built-in `/code-review`. After adding or updating a skill in `.agents/skills/`, re-copy it to `.claude/skills/`.
